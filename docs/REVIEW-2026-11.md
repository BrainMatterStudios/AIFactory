# AIFactory review and redesign analysis

**Date:** 2026-11-20
**Scope:** the current AIFactory codebase and roadmap, the transcript-analytics
handover, and what a leaner factory built for current frontier models should
look like.
**Companion:** the revised [ROADMAP.md](ROADMAP.md) turns this analysis into a
sequence of work.

---

## 1. Summary

1. **The factory became slow because its process was designed for weaker
   models, and every hardening round added more of it.** A T2 `factory build`
   chains roughly 6 to 10 separate model sessions: contract author, design
   author, implementer, reviewers, 2 to 3 judges, and up to 2 revise cycles.
   It also pauses twice for digest-bound human approvals. Each session starts
   cold and rebuilds context that a single long session would already have.
   Current models (Opus 5.5, Fable 5.2, GPT-5-class Codex) plan, implement,
   test and self-correct inside one session better than a relay of personas
   does.
2. **About 80% of the code is unproven ceremony.** Of roughly 66K source lines,
   about 52K are `build/`, `execution/`, `core/design`, `core/contracts` and
   `analyzers/`. That is the experimental autonomous builder and its
   containment backends, none of which has run in production. The
   production-derived part (`loop/`, the adapters, the orchestrate helpers) is
   about 6K lines. The repository grew by about 169K lines and shrank by 6.5K
   in three months.
3. **The roadmap compounds the problem.** Releases 0.4 to 0.8 add quality
   obligations, an exploratory tester, a review canvas, managed adoption and
   governed evolution. Every one of them is another stage. The roadmap's own
   principle, that a stage which cannot show it improves reliability, cost or
   review burden should be removed, was never applied, because the measuring
   tool never got built.
4. **The handover's direction is right, with five adjustments** (§4): stop
   losing transcripts today, redact before anything leaves a laptop, calibrate
   the LLM pass instead of defaulting to the smallest model, add a queryable
   analytic store next to Grafana, and route weekly findings through the
   existing harvester so recurring problems update one issue instead of filing
   duplicates.
5. **Keep the parts that earned their place:** the doctrine's single rule (the
   human owns what cannot be undone), gates enforced as code through CI and
   branch protection, the observe→diagnose→queue loop with fingerprint dedup,
   the secret scanner, and the candour of KNOWN_ISSUES. Freeze and archive the
   rest.

### 2.2 Why it got slow: the per-issue path

```
issue → classify tier → contract-author (Opus) → intent gate → [human: approve contract digest]
      → design-author (Opus) → harness analyzer → design gate → [human: approve design digest]
      → implementer (Sonnet) → verify_cmd → findings_v2 reviewers (n personas)
      → judge panel (2–3 × Opus, incl. security veto) → combine
      → REVISE? (×2) → re-verify → design gate refresh → secret scan → PR
```

Every arrow between agent roles is a cold handoff. Each new session re-reads
the issue, the contract and the design, then re-explores the repository. The
artifacts passed between them (Contract v2, Design IR) are strict schemas
that the models must satisfy before any code exists, so a meaningful share of
tokens goes to satisfying the process rather than the task. The two approval
pauses turn a 20-minute task into a multi-hour one whenever nobody is watching
the queue.

This structure made sense when it was designed: models drifted over long
contexts, judged their own work leniently, and lost track of scope. The current
generation runs multi-hour sessions coherently, verifies by running tests, and
takes review from a second model in one pass. The scaffolding now costs more
than the failures it prevents. The team has decided to act on this
judgement without a formal comparison (§5). The analytics module (§3) then
tunes the lean design.

### 2.3 Why the development process itself got slow

The repository's history shows the same pattern in how the factory was built:

- brainstorm → spec → 500 to 2,000-line implementation plan →
  subagent-driven implementation → multiple adversarial review panels per
  change (eight rounds on the builder alone);
- each hardening round fixed real defects and introduced new surface for the
  next round (KNOWN_ISSUES describes this candidly);
- since August, almost all work has gone into governance machinery (digests,
  approvals, containment, replay) rather than into anything that shipped
  features in a product repository.

A lean process for current models looks like this. Write a one-page brief, or
a GitHub issue with acceptance criteria. Run one agent session that plans,
implements and tests. Open a PR, let CI run, get one independent review pass
(ideally from the other vendor's model), and have a human merge. Long design
documents only for work that spans weeks, and still kept to one or two pages.

### 2.4 What to keep, and why

| Keep | Reason |
|---|---|
| **The doctrine's rule:** the human owns production releases, scope, and policy | Still correct, and independent of model strength |
| **"Gates are code, not instructions"** | Now enforced more cheaply by CI, branch rulesets, CODEOWNERS and native agent permission settings than by 50K lines of controller |
| **`loop/` observe → diagnose → queue** | Production-proven. The analytics module is the same loop pointed at the factory |
| **`harvester` fingerprint dedup and recurrence handling** | Exactly what the weekly synthesis needs so it doesn't refile the same struggle every week |
| **`collectors` contract `{name, verdict, evidence}`** | A small, stable interface between analytics and issue filing |
| **Secret and public-content scanners** | Reused to redact transcripts before upload |
| **`spend.py` role classification** | A starting point for cost-per-stage reporting |
| **`MODEL_TIERING.md` finding (archived):** cheap models silently under-cover input-heavy work | Directly relevant to choosing the transcript-classifier model (§4.3) |
| **KNOWN_ISSUES candour** | Keep the habit. Drop the machinery it was documenting |

## 3. The analytics module: recommended shape

### 3.1 Placement and interface

Put it in its own top-level package in this repository (working name
`insights/`, Python package `aif_insights`) with its own `pyproject.toml` in a
uv workspace. **It must not import `software_factory`.** Add an import-boundary
test like the existing `tests/test_import_boundaries.py` to enforce that. Its
only output contract toward the factory is a findings file in the existing
collector shape:

```json
{"name": "struggle/test-loop", "verdict": "WARN",
 "evidence": {"sessions": 14, "share": 0.18, "examples": ["s3://…/abc.jsonl"]}}
```

The factory's harvester, or the VPS fleet agent, can consume that file and
file or update GitHub issues, with dedup. This keeps the module reusable on
its own and leaves the factory as an optional consumer.

### 3.2 Internal interfaces

| Interface | Responsibility | First implementations |
|---|---|---|
| `TranscriptSource` | List new raw sessions since a checkpoint | `ClaudeCodeSource`, `CodexSource` (later: CI/headless runs, cloud sessions) |
| `normalize()` → `Session` | One agent-neutral schema: ids, agent and version, user, machine, repo, cwd, branches, timestamps, models, turns, tool calls (name, ok, duration, error class), user messages (interrupt, correction), tokens, estimated cost, subagent links | One adapter per agent format |
| `extract()` → `SessionSignals` | Deterministic signals only, with no model calls | Pure functions, unit-tested against fixture transcripts |
| `digest()` → `SessionDigest` | A compact timeline (5 to 20K tokens) for the LLM: user asks, corrections, errors, test runs, final state. **Never the raw transcript** | Deterministic |
| `Assessor` | Rubric → JSON assessment | Batch API with structured outputs (`output_config.format`) |
| `Joiner` | Session ↔ commits ↔ PR ↔ CI runs ↔ Dokploy deploy | GitHub API, Dokploy API or webhook log |
| `Sink`s | Archive, metrics, findings | S3-compatible bucket, Grafana Cloud (OTLP), findings JSON |

### 3.3 Storage layout

```
s3://<bucket>/
  raw/{agent}/{user}/{yyyy}/{mm}/{dd}/{session_id}.jsonl.zst      # redacted, immutable
  raw/{agent}/{user}/…/{session_id}/subagents/*.jsonl.zst         # sidechains kept with parent
  derived/sessions/dt={date}/part-*.parquet                       # Session + SessionSignals
  derived/assessments/rubric={v}/dt={date}/part-*.parquet         # LLM output, versioned by rubric
  derived/joins/dt={date}/part-*.parquet                          # session↔PR↔CI↔deploy edges
  reports/weekly/{yyyy}-W{ww}.md
```

Parquet plus DuckDB gives ad-hoc SQL over every session at no server cost.
Grafana is good for KPIs over time but poor for "show me every session where
the agent looped on the same failing test". The weekly synthesis agent queries
DuckDB directly.

**Grafana cardinality rule:** session IDs, branch names and file paths go into
**logs** (Loki), never into metric labels. Metric labels stay at user, agent,
model, repo, outcome, and rubric category.

### 3.4 Deterministic signals: start here, before any LLM

Each of these can be computed from the transcript alone:

- **User interrupts.** Interrupt markers in the transcript, Esc mid-turn.
- **User corrections.** The next user message after an assistant turn
  contradicts it ("no", "that's wrong", "revert", "I said…"). A cheap
  classifier is fine for this narrow job once it has been calibrated.
- **Tool error rate**, by tool and error class (edit failed to apply,
  command not found, permission denied, timeout).
- **Retry loops.** The same command, or the same failing test, run 3 or more
  times. Edit→test→fail cycles on the same file.
- **Test outcomes.** Exit codes of test commands detected from tool calls.
- **Session shape.** Wall-clock time, active versus idle gaps, turns, tokens,
  cache-hit ratio, estimated cost, subagent count and share of tokens,
  compactions.
- **Outcome proxies.** Commits made, branch pushed, PR opened (from the join).
  A session that ends with none of these is a candidate "abandoned" session.

### 3.5 Privacy and security (not in the handover; required)

Transcripts contain whatever the agents read: client code, `.env` files, keys
pasted into prompts, customer data from database queries.

1. **Redact before anything reaches the bucket,** using the existing secret
   patterns (`core/publication.py`, the build secret scanner) plus a
   high-entropy check. For laptop sync, redact on the laptop. For
   Compliance API pulls, redact in the worker before writing.
2. The bucket is private, encrypted server-side, versioned, and readable only
   by the worker's service credentials and the two of you. Consider object
   lock for the raw prefix, since it is meant to be a permanent archive.
3. Keep prompt content out of Grafana at first (`OTEL_LOG_USER_PROMPTS` off).
   Grafana gets metrics and categorical tags. Content stays in the bucket.
4. Support an exclusion list for client repositories whose contracts forbid
   off-machine storage of their code.
5. The two developers should explicitly agree that each can read the other's
   transcripts. The analysis is about the factory, not about people, so the
   KPIs should be reported per agent and per stage, not as a leaderboard.

## 4. Review of the proposed pipeline

### 4.0 Verified collection facts (checked 2026-11-20 against official docs)

**Claude Code telemetry** ([monitoring-usage](https://code.claude.com/docs/en/monitoring-usage))

- Enable with `CLAUDE_CODE_ENABLE_TELEMETRY=1`, `OTEL_METRICS_EXPORTER=otlp`,
  `OTEL_LOGS_EXPORTER=otlp`, `OTEL_EXPORTER_OTLP_ENDPOINT`,
  `OTEL_EXPORTER_OTLP_HEADERS`. Traces are beta:
  `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1` plus `OTEL_TRACES_EXPORTER=otlp`.
- `OTEL_METRICS_INCLUDE_REPOSITORY=true` adds repository attributes, and
  `OTEL_RESOURCE_ATTRIBUTES` can add `team.id` or `machine`.
- Content flags (`OTEL_LOG_USER_PROMPTS`, `..._ASSISTANT_RESPONSES`,
  `..._TOOL_DETAILS`, `..._RAW_API_BODIES`) are all off by default. Keep them
  off.
- Metrics:
  - `session.count`, `cost.usage` (an estimate), `token.usage`
  - `lines_of_code.count`, `commit.count`, `pull_request.count`
  - `code_edit_tool.decision`, `active_time.total`
- Events:
  - `user_prompt`
  - `tool_result` (success, duration, error type)
  - `api_request`, `api_error`, `api_refusal`
  - `tool_decision`
  - `subagent_completed`
- These variables are **ignored in a repository's `.claude/settings.json`**.
  Put them in Enterprise managed settings (admin console or
  `managed-settings.json`) so both machines get identical configuration.

**Claude Code transcripts** ([sessions](https://code.claude.com/docs/en/sessions), [hooks](https://code.claude.com/docs/en/hooks))

- Location is `~/.claude/projects/<encoded-cwd>/<session>.jsonl`. Anthropic
  documents the record format as internal and subject to change, so the
  parser must be version-tolerant.
- **Default retention is 30 days.** Raise it with `cleanupPeriodDays`.
- `SessionEnd` hooks get a 1.5 s default budget (up to 60 s with a timeout
  set), and the transcript may still be flushing when they run. Use the
  nightly sweep as the primary path and the hook only as a fast path.
- Headless runs (`claude -p`) also write transcripts unless
  `--no-session-persistence` is passed.

**Enterprise admin data** ([analytics](https://platform.claude.com/docs/en/manage-claude/analytics-api), [compliance](https://platform.claude.com/docs/en/manage-claude/compliance-sessions))

- The **Claude Enterprise Analytics API** returns per-user daily sessions,
  commits, PRs, lines, and tool accept/reject counts. It is about a day
  behind, and needs a key from the primary owner. It provides free baseline
  KPIs.
- The **Compliance API** (Enterprise only) returns transcripts of Claude Code
  sessions run on users' machines under the Enterprise login, retained for 6
  years by Anthropic. It excludes cloud and ZDR sessions.
- **This could replace laptop sync for Claude Code entirely.** The worker
  would pull from the API, redact, and archive. Check fidelity against a local
  JSONL file before deciding, in particular whether subagent sidechains and
  tool results are included. Whether API-key, CI or `-p` runs are captured is
  unconfirmed.

**Batches and structured outputs** ([batch](https://platform.claude.com/docs/en/build-with-claude/batch-processing), [structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs))

- Batches are 50% off, usually finish in under 1 hour, and are always done
  within 24 hours.
- Structured outputs (`output_config.format: json_schema`) are stable. Schemas
  need `additionalProperties: false` and cannot use `oneOf` or numeric/length
  bounds; the rubric schema above complies.

**Codex: not verified.** OpenAI's docs host was unreachable from this
session. Third-party sources describe an `[otel]` section in
`~/.codex/config.toml` with prompt logging off by default, and rollout files
under `~/.codex/sessions/YYYY/MM/DD/`. Confirm both against
developers.openai.com before building the Codex adapter.

| Step | Handover proposal | Assessment and changes |
|---|---|---|
| **Collect** | Claude Code OTel → Grafana; sync `~/.claude/projects` and `~/.codex/sessions` to the bucket | Right in direction, with changes (§4.0). (a) Raise Claude Code's 30-day transcript retention **today**. (b) Evaluate the Enterprise **Compliance API** as the primary Claude Code source before building laptop sync. (c) For laptop sync, use a nightly sweep as the primary path, because a `SessionEnd` hook has a 1.5 s default budget and the transcript may still be flushing. (d) Put the telemetry settings in managed settings: they are ignored in a repo's `.claude/settings.json`. (e) Include subagent sidechain files. (f) Codex OTel export as well as its files. (g) Cloud and CI sessions need their own path |
| **Nightly worker** | Deterministic signals, then an LLM rubric pass on the Batch API with a small model by default | The two-stage design is right. **Change the default model choice** (§4.3). Run on the VPS through Dokploy as a scheduled container, the same pattern as the fleet agent, rather than in GitHub Actions: it needs bucket credentials and must poll batches |
| **Join** | Session → branch, PR, CI, deploy | Right, but it is many-to-many. One PR often spans several sessions and agents, and one session may touch several branches or none. Store join *edges* with an attribution weight and compute KPIs from the edges. Use transcript `cwd` and `gitBranch`, commit trailers (`Co-Authored-By`), and PR head refs |
| **Output** | Tags → Grafana metrics and logs; JSON next to transcripts | Right. **Add** the Parquet/DuckDB layer (§3.3) and the cardinality rule |
| **Weekly synthesis** | Report plus GitHub issues proposing factory changes | Right. **Route the issues through the harvester's fingerprint dedup** so a recurring struggle updates one issue with a recurrence count. Every proposal must name the KPI it expects to move, so next month's data can confirm or refute it. Cap it at 3 to 5 proposals per week |

### 4.1 Corrections to the KPI list

| KPI | Definition to use | Caveat |
|---|---|---|
| Cost per merged PR | Σ attributed session cost ÷ merged PRs | On Enterprise seats and ChatGPT plans this is *token-equivalent* cost, not invoice cost. Label it that way |
| First-pass CI rate | PRs whose first CI run on the first pushed head is green | Exclude docs-only PRs or report them separately |
| Rework rate | PRs with follow-up commits after review, or fix-PRs touching the same lines within 14 days | Define one version and keep it |
| Correction loops per session | User corrections plus interrupts per session | The single best struggle signal |
| DORA (lead time, deploy frequency, change-fail rate, MTTR) | From PR→merge→Dokploy deploy events | With 2 developers the sample is small. Read these as trends, never as targets |
| Time per factory stage | From OTel spans or session segmentation | Only meaningful while the old factory is being measured |
| **Add: human attention per merged PR** | Minutes of active human input (prompting, reviewing, correcting) per merged PR | The KPI that matters most for autonomy |
| **Add: abandoned-session rate** | Sessions with no commit, PR, or explicit "done" | Separates exploration from failure |
| **Add: autonomy span** | Median minutes an agent works between human interventions | Directly measures "less scaffolding, more autonomy" |

Avoid tokens per line of code and lines of code per day. They reward the wrong
behaviour.

### 4.2 The rubric (draft v0, to calibrate)

The LLM sees the `SessionDigest`, never the raw transcript, and returns
schema-constrained JSON:

```json
{
  "task": {"kind": "feature|bugfix|refactor|investigation|ops|docs|other",
           "summary": "≤20 words", "repo_area": "free text"},
  "outcome": {"status": "completed|partial|abandoned|failed",
              "evidence": "what in the digest shows it"},
  "struggles": [{
    "category": "env_setup|tool_misuse|test_loop|spec_ambiguity|wrong_approach|context_loss|
                 missing_knowledge|flaky_ci|permission_friction|scope_creep|model_error|other",
    "turn_range": [12, 31],
    "description": "≤40 words",
    "root_cause": "repo_docs|agent_config|tooling|task_spec|model_capability|external|unknown",
    "fix_hint": "the cheapest change to the factory/repo that would have prevented it"
  }],
  "human_corrections_justified": "all|some|none|n/a",
  "confidence": "low|medium|high"
}
```

Root causes are deliberately things the factory can change (`repo_docs` means
CLAUDE.md or AGENTS.md, `agent_config` means settings, hooks and skills,
`tooling`, `task_spec`). That makes every finding actionable.

### 4.3 Which model for the rubric pass

Current list prices per million tokens (input/output): Haiku 5.5 $0.10/$0.50,
Sonnet 5.5 $2/$10, Opus 5.5 $4/$20. Message Batches take 50% off. At an
estimated ~1,000 sessions a month, with a 30K-token digest and 2K tokens of
output each, the whole nightly pass costs roughly **$2/month on Haiku, $40 on
Sonnet, $80 on Opus**.

At this volume **cost should not decide the model; accuracy should.** The
repository's own tiering research found the cheap tier fails silently by
under-covering, and diagnosing a struggle's root cause in a long session is
exactly that kind of task. Recommendation:

1. Hand-label about 30 sessions together (an afternoon).
2. Run Haiku 5.5, Sonnet 5.5 and Opus 5.5 on them through the batch API.
3. Use the cheapest model that matches human labels on `outcome.status` at
   least 90% of the time and on primary `struggles[].category` at least 75%.
   Until then, default to **Sonnet 5.5**.
4. Run the weekly synthesis on **Opus 5.5** (or Fable 5.2). It is one call a
   week over aggregated data, so cost is irrelevant and quality is everything.
5. Re-run the calibration set whenever the rubric version or model changes. The
   `rubric={v}` path partition keeps old and new assessments comparable.

Use structured outputs (`output_config.format` with a JSON schema). Forced
`tool_choice` returns an error on the current model generation.

## 5. The lean factory

**Decision (2026-11-20):** move to the lean factory now and build analytics in
parallel, with no head-to-head comparison against the old factory. This
replaces the handover's "analytics first" ordering. The data now tunes the
lean factory instead of deciding whether to build it.

### 5.1 Target shape: Factory v1 (lean)

```
Observe (scheduled agents, prod + factory) ─► GitHub issue (deduped, ready label)
      ─► ONE agent session per issue (Claude Code headless or Codex exec, native sandbox)
           plans → implements → runs tests → opens PR (writes a short plan in the PR body;
           pauses for a human only when classify_tier says "large feature" — scope gate)
      ─► CI: tests, lint, secret/public scan  +  ONE independent review (other vendor's model)
      ─► human merges to main / triggers Dokploy deploy   (unchanged ceiling)
      ─► analytics observes every session ─► weekly proposals ─► CLAUDE.md / skills / hooks
```

| Concern | Old mechanism | Lean replacement |
|---|---|---|
| Scope control | Contract v2 + intent gate + digest approval | Issue acceptance criteria. For large features, a short plan comment that a human approves with a label or reply |
| Design quality | Design IR + harness analyzer + design gate | The agent plans in-session. Review checks design. Analytics measures `wrong_approach` struggles |
| Correctness | findings_v2 reviewers + 2–3 judges + revise loop | Tests in CI + one cross-vendor review pass + human merge |
| Can't merge or deploy | Loop has no merge method + runner deny list | Branch rulesets on `main`, a GitHub App or token without merge or admin rights, and native permission settings that deny the release verbs. Enforced by the platform, not by our code |
| Containment | Lima/Leash cells, pnpm staging (18K lines) | Claude Code / Codex native sandboxing, managed settings, a VPS runner with least-privilege credentials |
| Model tiering | 19-persona catalog with tier locks | One strong model per session. A second, different model for review |
| Learning | Proposed 0.7 "governed evolution" | The analytics weekly loop, now and cheaply |

Expected size: roughly 6 to 8K lines (`loop/`, adapters, a slim CLI, the
dispatcher) plus the analytics package, down from about 66K.

### 5.2 What data would change this plan

- If sessions on large features show high `wrong_approach` or `scope_creep`
  rates, strengthen the plan gate. Don't bring back the panels.
- If single-reviewer PRs show a materially higher rework rate than the
  baseline, add a second review lens. Measure it again before it becomes
  the default.
- If `env_setup` or `permission_friction` dominate, the fix is harness
  configuration (devcontainers, managed settings), not process.

### 5.3 Measuring the old factory: dropped

The comparison of the old factory against a single session was dropped by
decision. The old factory's history stays in the `v0.3-archive` branch. The lean
factory's own first weeks of data serve as its baseline.

## 6. Risks

| Risk | Mitigation |
|---|---|
| Analytics turns into the next over-built system | Hard scope: no authority, no approvals, no digests. A read-only observer. Target ≤3K lines for v1 and ship within weeks |
| Secrets or client code leak into the archive or Grafana | Redact on the laptop, private encrypted bucket, no prompt content in Grafana, repository exclusion list |
| Losing history before collection starts | Raise retention and back up `~/.claude/projects` and `~/.codex/sessions` today |
| Small sample with 2 developers | Trends and per-session diagnosis, not significance tests. Pool across months |
| LLM tags are wrong in ways nobody notices | Calibration set, versioned rubric, confidence field, and periodic spot checks of 5 random sessions a week |
| Deleting the old factory loses something useful | The `v0.3-archive` branch was created before deleting. Anything needed later can be restored from it |
| Tool format drift (Claude Code and Codex transcript schemas change) | Adapters are versioned and tolerant. Unknown record types are counted and reported, never silently dropped |
