# AIFactory 0.2.0: architecture before code

**Release date:** 2026-08-09

**Status:** final GitHub release

The `findings_v2` parser, authenticated findings-only sensor dispatch,
deterministic routing, semantic publication replay, all-exit scratch cleanup,
and adversarial tests described here passed the documented release gates. The
source release is distributed through the protected `0.2.0` GitHub tag and
release. It is not published to PyPI or another package registry.

Version 0.2.0 adds an enforceable architecture-before-code boundary to the
experimental autonomous builder. For non-trivial work, the controller obtains a
structured Contract v2 document, runs deterministic intent policy, freezes the
accepted contract, and only then permits planning or implementation.

## Why freeze intent first

An implementation can be internally consistent and still solve the wrong
problem. Once code exists, reviewers are biased toward repairing that code rather
than revisiting its premise. Contract v2 therefore declares scope, non-goals,
risks, ambiguities, invariants, failure modes, irreversible effects,
dependencies, and acceptance coverage before implementation. The controller
commits and hashes an admissible contract as a checkpoint. Later phases must
preserve that exact digest; a restart discards the failed implementation but
keeps the accepted intent.

This is a control over declared intent, not proof that the declaration is true.
Schema conformance is not semantic truth. An omitted risk, false claim, or weak
acceptance criterion can still pass a structural validator.

## Why models observe and deterministic code decides

Models are useful at noticing cross-cutting defects, but natural-language
verdicts are an unsafe authority surface: a quoted template, contradictory
sentence, missing report, or failed invocation can be mistaken for approval.
Under `findings_v2`, each required sensor writes a strict report containing its
configured identity and typed findings. The controller freezes that report
against the exact reviewed artifact fingerprint. Pure policy then maps severity,
category, sensor availability, artifact immutability, and objective gate state to
the next disposition.

The separation is deliberate:

| Surface | Role | Authority |
|---|---|---|
| Contract author | Declares intent and unresolved questions | None to approve its own artifact |
| Intent policy | Checks declared predicates | Owns intent disposition |
| Review sensor | Emits observations and evidence locations | None to emit `PASS`, `REVISE`, or `BLOCK` |
| Review router | Applies pinned rules to frozen reports | Owns review disposition |
| Operator | Accepts a human-owned exact artifact | Owns the recorded approval decision |

Deterministic disposition does not make model observations deterministic or
correct. Missing and malformed evidence fails closed, while false negatives and
false positives remain possible.

## Why exact digests carry authority

Names and labels identify workflow state, not content. A label can remain while
the artifact changes, and a model can claim an approval it does not possess.
AIFactory canonicalizes authority-bearing JSON, records a SHA-256 digest, and
requires exact matches. A T2 plan approval also records the parent contract
digest, so a contract change invalidates the plan authority.

The CLI commands are provider-neutral. These examples use deliberately
synthetic digests:

```bash
factory approve contract demo-42 aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa \
  --approver demo-operator --reason "synthetic intent review"

factory approve plan demo-42 bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb \
  --parent aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa \
  --approver demo-operator --reason "synthetic plan review"
```

Approval records identify what the local controller accepted. They are not
cryptographic identity signatures. The build's printed approval command assumes
Git supplies `user.email` or `user.name`; if neither exists, add an explicit
`--approver <operator-identity>`.

Contracts that need human authority have two controller states. Before approval,
the exact text, parsed document, digest, repository/issue identity, and policy
version are stored as **pending**. A later run materializes those exact bytes in a
fresh worktree, re-runs validation and policy, and checks current approval without
dispatching the contract author. A matching approval permits the checkpoint and
atomically promotes that exact pending generation to **accepted**.

Accepted is artifact state, not permanent approval. Every run re-checks the
current approval record. Removing approval makes the accepted digest
`APPROVAL_PENDING` again without re-authoring. Replacing approval with a
different digest is a mismatch and blocks. Pending/accepted records themselves
are descriptor- and digest-authenticated; changing accepted intent requires a
stopped, backed-up, audited manual replacement of contract state and any dependent
plan state before the normal author/checkpoint/approval lifecycle resumes.

## Why controller evidence is outside the worktree

The runner can write the build checkout, so a file inside that checkout cannot
independently prove approval, policy outcome, or review evidence. Approval
records and append-only decision events therefore use
`factory.build.state_dir` when configured; that manifest field overrides
`FACTORY_STATE_DIR`, which in turn overrides the controller default. This root is
outside the repository and registered build worktrees. Exact pending/accepted
contracts and contract-bound plans are separate controller-owned, ignored local
state under the canonical checkout's `.factory` directory, outside the disposable
runner worktree. Runner prompts do not receive these locations. Events are
redacted before persistence and chained by digest.

Directory separation is not an OS security boundary. On an unrestricted shared
host, a runner may still read or modify controller files and credentials. Real
authority separation requires process isolation or sandboxing, filesystem
permissions, and least-privilege credentials supplied by the operator. The event
chain detects later alteration during replay; it is not an externally witnessed
or signed log.

## Why the public/private boundary is a CI gate

A correct implementation can still be unsafe to publish. The public repository
accepts generic code, synthetic fixtures, public citations, and reviewed license
statements. It rejects private operational material, credentials, internal
locations, generated evidence, escaping links, and unexpected binaries. CI runs
the tracked-file scanner so publication safety is an explicit release property,
not a final-memory exercise.

The scanner checks the current tree and can inspect every commit after a reviewed
base. A clean current tree does not make unsafe intermediate commits publishable.
The release gate therefore also requires a clean history-range scan and human
inspection of the exact diff and tracked-file manifest. See
[PUBLIC_CONTENT_POLICY.md](../PUBLIC_CONTENT_POLICY.md).

## Lifecycle in 0.2.0

```text
issue -> tier -> isolated worktree -> Contract v2 author
      -> deterministic intent gate
      -> SPEC_PENDING / exact contract approval when required
      -> frozen contract checkpoint
      -> T2 plan + exact plan-and-parent approval when applicable
      -> implementation -> objective verification
      -> findings_v2 sensors -> deterministic review routing
      -> re-verification -> objective secret scan -> PR into a non-production base
```

The in-build scan checks the produced Git blobs for high-signal secret shapes. It
does not run the complete public-content policy. Current-tree and history-range
public inspection remain separate local/hosted CI and release gates.

At every active lifecycle authority boundary, unreadable, unknown, stale,
mismatched, or corrupt required state stops progress. The builder still has no
permission to merge or deploy, and protected `main` remains a required
server-side release control.

## Migration

### Contract v1 to Contract v2

Contract v1 remains readable during v0.x and emits a `DeprecationWarning`. It is
a compatibility path only. New and migrated projects should regenerate or edit
contracts to `schema_version: 2`, add the required `intent` object, assign stable
unique IDs, pin dependency versions exactly, and make acceptance criteria cover
every invariant and irreversible operation. Remove the v1
`approved_git_rev` field: the controller-owned checkpoint and digest replace it.

Changing a contract creates a new digest. Re-run intent policy, obtain any newly
required contract approval, regenerate the T2 plan from that exact contract, and
approve the new plan digest with the new parent digest. Never carry approval
forward by filename or label.

### `verdict_v1` to `findings_v2`

Set the current protocol explicitly:

```yaml
factory:
  build:
    require_contract: true
    review_protocol: findings_v2
```

`verdict_v1` remains supported during v0.x only for compatibility and emits a
deprecation warning. A manifest with no `review_protocol` is interpreted as the
same deprecated compatibility mode. New scaffolds select `findings_v2`.
Custom runners must allow the configured review sensor to write its one scratch
findings file while preventing it from changing the reviewed artifact surface.

Finding overrides are not silent configuration. An operator-authorized override
must name the exact artifact fingerprint and finding ID and include authority and
rationale in the decision history. A stale override does not apply to a changed
artifact. The approval CLI above approves contract and plan artifacts; it does
not turn a review finding into an approval.

## Threat model and limits

### Architecture and correctness

- The policy checks declared intent; it cannot prove omitted facts or the
  adequacy of a proposed mechanism.
- `findings_v2` removes verdict authority from model prose but cannot guarantee a
  sensor notices a real defect or avoids a false positive.
- Version 0.2.0 does not include a general design intermediate representation, a
  separate deterministic design gate, universal third-party analyzer adapters,
  code-to-intent re-extraction, or automated policy discovery.
- Existing code scanners can supply another evidence layer, but integrating all
  such scanners into a universal deterministic gate is deferred.

### Security and authority

- State outside a worktree is organizational separation unless the runner is
  sandboxed from it.
- The reference runner's command deny list is pattern matching, not a sandbox.
- Secret and public-content scanners are denylist backstops and may miss novel
  sensitive data. Human review remains mandatory.
- Approval identity comes from explicit CLI input or local Git identity and is
  not cryptographically authenticated.
- Prompt injection remains possible wherever untrusted issue or contract text is
  shown to a model; deterministic gates limit its authority but do not make the
  text safe.
- Branch protection is enforced by the hosting provider, not this package.

### Compatibility and operation

- Contract v1 and `verdict_v1` are supported only as deprecated v0.x
  compatibility paths. Removal requires a future major release.
- The development branch must exist locally; the builder does not fetch it.
- One build runs per repository. An interrupted stale-lock reclaim may require a
  human to inspect and remove the abandoned reclaim marker.
- Spend caps bind only when a runner reports finite cost and are not
  concurrency-safe across projects sharing a state directory.
- Controller-state corruption blocks progress. Complete recovery backups include
  approvals, decisions, pending/accepted contracts, and stored plans. An approval
  does not become cryptographically invalid merely because its decision log is
  missing, but audit continuity and state completeness are then lost and must not
  be claimed. Never repair continuity by editing or truncating authority records.
- The separate full public-content current-tree scan does not certify Git
  history. A separately reviewed history range must be clean before any push or
  release.

This is an engineering implementation rather than scientific validation. The
project does not claim that structured intent reliably improves software. The
autonomous builder remains experimental; use the human-supervised doctrine path
for important work and do not schedule the builder unattended.
