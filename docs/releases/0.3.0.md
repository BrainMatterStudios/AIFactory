# AIFactory 0.3.0

**Release date:** 2026-08-11

**Status:** local release candidate; publication actions remain separately approved

Version 0.3.0 adds a design-authority spine to the experimental autonomous
builder. It represents architecture as strict Design IR v1, checks exact
Contract parentage and runner feasibility, normalizes bounded analyzer evidence,
applies a deterministic Design gate, and requires human approval of the exact
Design digest before implementation. Read-only inspection and status surfaces
project that authority without becoming another state store.

The autonomous builder remains experimental and is not production-proven or
scientifically validated. The human-supervised doctrine remains the recommended
path for important work.

## Lifecycle and authority

The adopted T2 lifecycle is:

```text
Contract v2 -> sticky workflow protocol -> Design IR v1
  -> declared/observed/effective capabilities -> bounded analyzer evidence
  -> deterministic Design gate -> exact Design-and-parent approval
  -> implementation -> findings-only review -> objective verification
  -> secret scan -> publication replay -> PR into a non-production branch
```

Contract, Design, configuration, capability assessment, repository fingerprint,
analyzer evidence, gate result, approval, and publication history are bound by
exact digests. A passing Design gate means declared deterministic policy was
satisfied for those inputs. It is not approval. Approval records bind the exact
repository, issue, artifact digest, and parent Contract digest. Changing
identity-bearing Design content creates a new digest and requires a new
approval; changing evidence makes the old gate stale and requires a fresh gate.

Models author proposals and observations. They cannot approve a Design, elevate
a runner capability, suppress required evidence, or choose the gate's passing
disposition. Local approval identity is not a cryptographic signature.

## What shipped

- Strict Design IR v1 validation, canonical SHA-256 identity, immutable
  controller-owned generations, exact parent checks, and exact approval.
- Trusted runner capability declarations plus runtime observations. Effective
  capabilities are a conservative intersection; observation can remove but
  never add an undeclared guarantee.
- A SARIF normalizer that does not execute the producer and a native harness
  analyzer for instruction, hook, permission, environment, and exposed-tool
  posture.
- A deterministic Design gate with replayable input identities and explicit
  `pass`, `block`, and `unavailable` results.
- `factory design validate <file>`, `factory design gate <file>`, `factory
  analyze <adapter>`, `factory capabilities`, and `factory status [issue]`, all
  with versioned `--json` output. `factory doctor` previews configuration,
  protocol, analyzer requirements, and capability gaps.
- One shared publication lifecycle verifier for legacy and Design workflows.

Inspection commands and status do not repair, refresh, approve, migrate, or
persist evidence. Exit `0` means the requested inspection succeeded and, where
applicable, is passing/ready/degraded/complete; exit `1` means a current runtime,
authority, unavailable, or deterministic non-pass result; exit `2` means invalid
invocation, input, or configuration.

Status states are `ready`, `approval_pending`, `blocked`, `degraded`,
`unavailable`, and `complete`. Conservative precedence is unreadable required
authority, deterministic integrity/policy blocks, exact approval, optional
degradation, readiness, then replay-bound completion. Status is a linearizable
"as observed" projection at its final observation point. It is not a filesystem
snapshot, repository lock, or authority that prevents a later writer.

The closed capability vocabulary covers isolated worktrees, external approval
pause, controller-state separation, artifact fingerprinting, bounded writable
paths, analyzer evidence, objective verification, credential scanning, merge
prohibition, and deployment prohibition. "Declared" means trusted adapter code
claims the guarantee, "observed" means a runtime check confirms or reduces it,
and "effective" is the conservative assessed set used by policy. Task text,
models, configuration prose, and analyzers cannot elevate it. The reference Echo
runner declares only merge/deployment prohibition; the Claude Code runner
declares none because its command filters are not sandbox guarantees.

## Required macOS limitation

Ordinary current macOS APFS Data volumes cannot prove the harness analyzer's
strict no-atime read requirement. When any supported harness file is present,
the analyzer therefore does not content-open it and emits constant high-security
fail-closed evidence. New scaffolds make the harness analyzer required, so this
blocks the Design gate on an ordinary current APFS volume.

Do not restore access times after reading: restoration is itself a mutation and
cannot prove no observer saw the intermediate state. Supported mitigations are
to place the inspected project on a volume or run in an environment with a
verifiable no-atime policy, and to preview the exact posture with `factory
doctor` before opting a new Contract parent into Design IR. Existing workflows
can remain on `legacy_plan`. Disabling or making the required analyzer optional
does not preserve the Design-authority guarantees of the shipped scaffold.

The quiet analyzer broker requires the multiprocessing `fork` start method. It
supports the release's macOS and Linux environments. Native Windows analyzer
execution is unsupported and fails closed as `unavailable`.

## Analyzer and storage threat model

Installed analyzers are trusted code, like installed plugins. Normalized
analyzer evidence does not sandbox installed analyzer code. The broker suppresses
adapter output, bounds time, process cleanup, frame count, bytes, encoding,
finding count, and schema, and rechecks the repository fingerprint. Persistent
workspace mutation is detected. Those controls cannot prove that analyzer code
performed no transient or external side effects, including temporary workspace
mutation.

The SARIF importer reads a descriptor-pinned, bounded evidence file and never
executes its producer. It validates every consumed field but is not a complete
SARIF JSON-schema validator. The harness analyzer uses supported fixed relative
paths, no-follow descriptors, bounded iterative JSON and shell inspection, and
constant secret-safe failure evidence. Analyzers can still miss defects or
report false positives.

Approvals, decisions, immutable Design generations, gates, and sticky protocol
records are controller-owned. They must be outside runner-writable worktrees,
backed up and restored as one lifecycle set, and authenticated before reuse.
Directory separation is not an OS sandbox. Use process isolation, filesystem
permissions, least-privilege credentials, and server-side protected production
refs. The reference runner's deny patterns and the fork broker are not general
containment boundaries.

The logical read-only claim for inspection and status covers content and
authority mutation, not access time. Portable no-atime reads are unavailable on
some platforms, and the commands do not restore timestamps.

## Migration and rollback

There is no automatic migration.

1. Run `factory doctor`, `factory capabilities`, and the relevant `factory
   analyze <adapter>` commands as a read-only preview. Existing manifests that
   omit `design_protocol` select `legacy_plan` and emit an actionable migration
   warning; they are not rewritten.
2. Validate that the runner supplies every required effective capability and
   that every required analyzer is available in the intended environment.
3. Set `design_protocol: design_ir_v1`, the Design-author role, and explicit
   analyzers only for a new exact Contract parent. The first selection is sticky
   for that repository, issue, and parent digest.
4. Exercise the real Contract -> Design -> gate -> exact approval path before
   relying on it.

To roll back, restore `legacy_plan` only for a later new Contract parent. An
existing parent keeps its recorded protocol, including an in-progress Design IR
workflow. Old Contract, Plan, Approval, Decision, Design, and gate records remain
readable and are neither converted nor erased. A legacy plan approval is never
inferred to be a Design approval.

Back up external approval/decision state and the canonical checkout's ignored
Contract, Plan, Design, gate, and protocol records together. On corruption, stop
builds, preserve the damaged state, restore a complete authenticated snapshot,
and replay every available decision chain. If no trustworthy snapshot exists,
select fresh state and re-establish current exact artifacts and approvals. Do
not splice, truncate, hand-edit, or auto-repair authority records.

## Explicit non-claims

- Schema validity is not design correctness. It cannot prove scope, declared
  facts, mechanisms, or coverage are true or complete.
- Analyzers can miss defects or report false positives; deterministic routing
  constrains authority, not sensor accuracy.
- Normalized analyzer evidence does not sandbox installed analyzer code.
- Local approval identity is not a cryptographic signature.
- Directory separation is not an OS sandbox.
- Version 0.3.0 supplies no merge, deploy, registry, self-learning, UI, or
  configuration ownership. It also performs no automatic analyzer remediation.

No branch push, pull request, merge, tag, GitHub release, registry publication,
or deployment is implied by this release candidate. Each remains a separately
approved shared-state action.

## Influence and provenance

The operator lifecycle and capability-visibility direction was conceptually
informed by [Everything Claude Code](https://github.com/affaan-m/ecc) at commit
`649def769bd860512e5fce86e30aa05c8119259f`. The adopted ideas are explicit
capability visibility, analyzer-style harness inspection, review-oriented
presentation, managed-lifecycle planning, and portable context. ECC is an
influence, not a vendored dependency or copied implementation; no ECC source or
assets are included. AIFactory's deterministic authority model, schemas,
implementation, and fixtures are original Apache-2.0 work.

The earlier architecture-first direction remains conceptually influenced by
[Tell Your Coding Agent to Work as an Architect First](https://github.com/styrumg/Architect-First-Article),
as documented in the [0.2.0 release notes](0.2.0.md).

## Package and compatibility

Core AIFactory still has zero hard third-party runtime dependencies:
`project.dependencies` is empty. YAML, GitHub, Postgres, and development tooling
remain explicit extras. Contract v1, Contract v2, `verdict_v1`, `findings_v2`,
legacy plans, and their existing records remain readable throughout the v0.x
compatibility line as documented; new guidance uses Contract v2, `findings_v2`,
and Design IR v1.
