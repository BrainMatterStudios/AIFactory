# AIFactory 0.3.0 design authority design

**Date:** 2026-08-10

**Status:** Approved design and written specification

**Target:** AIFactory 0.3.0

## Summary

Version 0.3.0 adds a structured design-authority layer between an approved
Contract v2 artifact and implementation. The release introduces Design IR v1,
a deterministic design gate, explicit runner capability contracts, normalized
analyzer adapters, exact design approval, and a read-only status projection.

The intended lifecycle is:

```text
approved Contract v2
    -> runner capability preflight
    -> Design IR v1
    -> analyzer evidence
    -> deterministic design gate
    -> exact human approval of the design digest
    -> implementation and acceptance evidence
```

The release preserves AIFactory's central authority split: models and tools
observe or propose, deterministic code applies declared policy, and a human
approves exact artifacts when authority is required.

## Recommendation and adversarial review

The selected approach is an **architecture spine**: establish stable design,
capability, evidence, and status contracts before building richer review or
management experiences.

Two alternatives were rejected:

1. **Operator-first 0.3.0.** Building a canvas, lifecycle manager, and memory
   first would make their state model depend on unstable artifacts and risk
   turning presentation state into authority.
2. **Omnibus 0.3.0.** Combining design authority, UI, configuration ownership,
   learning, and packs would be too large to review adversarially and too hard to
   migrate or roll back safely.

The architecture-spine approach is smaller, closes capabilities already deferred
by the 0.2.0 design, and provides versioned interfaces on which 0.4.0 and later
releases can safely build.

## Goals

- Represent a proposed software design as strict, versioned data.
- Prove that the design refers to the exact approved Contract v2 artifact.
- Check design completeness, traceability, evidence, and runner feasibility with
  deterministic policy.
- Prevent a runner or model from claiming guarantees the active environment does
  not provide.
- Normalize third-party analyzer observations without granting them disposition
  authority.
- Require exact human approval of the design that implementation will follow.
- Give operators a concise, reconstructable view of current state and blockers.
- Preserve 0.2.0 projects and in-progress runs without silent migration.

## Non-goals

Version 0.3.0 does not include:

- a graphical Review Canvas;
- managed installation, repair, or uninstall of harness configuration;
- code-to-design re-extraction;
- automated discovery or admission of policy improvements;
- cross-runner memory or capability packs;
- automatic remediation of analyzer findings;
- remote approval bots, merge, deployment, or publication authority;
- a second workflow database.

These boundaries keep the release coherent and are recorded in
[the roadmap](../../ROADMAP.md).

## Authority model

The authority order is:

1. A human approval authorizes an exact Contract or Design IR digest.
2. A deterministic gate determines whether declared policy is satisfied.
3. Runner and analyzer outputs are untrusted evidence.
4. Status and review surfaces are projections with no authority.

A model may author Design IR content. It may not approve that content, suppress
required evidence, select a passing disposition, or elevate runner capabilities.

## Design IR v1

### Document shape

Design IR v1 is strict JSON. Its top-level fields are:

- `schema_version`: integer `1`;
- `issue`: the source issue identity;
- `repo`: the normalized repository identity;
- `generated_at`: informational timestamp excluded from the artifact digest;
- `tier`: `T2` for the initial release;
- `parent_contract_digest`: the exact canonical Contract v2 SHA-256 digest;
- `summary`: concise design intent;
- `required_capabilities`: capabilities asserted as additionally required by the
  design;
- `components`: bounded units and their responsibilities;
- `interfaces`: contracts between components or external systems;
- `data_flows`: classified movement of data across components or boundaries;
- `security_boundaries`: assets, trust assumptions, controls, and failure
  responses;
- `deployment_assumptions`: environmental assumptions and their validation
  obligations;
- `decisions`: choices, alternatives, rationale, and consequences;
- `risks`: conditions, impact, mitigations, and evidence obligations;
- `open_questions`: unresolved, resolved, or delegated design questions;
- `traceability`: links from Contract v2 criteria and intent IDs to design
  elements and evidence obligations.

Every nested record has a stable non-empty `id`. IDs are unique across the
document, and all references must resolve. Unknown fields, bool-as-int values,
duplicate IDs, invalid enums, empty required text, and unsupported versions are
errors rather than warnings.

The implementation plan may divide validation across focused modules, but it
must not weaken this external document contract.

### Canonical identity

The Design IR digest is SHA-256 over compact, UTF-8, key-sorted JSON after
removing only `generated_at`. The document does not contain its own digest.
Repository, issue, parent contract, architecture, traceability, risks,
questions, decisions, and required capabilities are all identity-bearing.

An authenticated controller-owned envelope stores the artifact bytes and digest
alongside repository, issue, parent digest, schema, design-policy version, and
configuration digest. The envelope is not part of the Design IR digest.

### Traceability rules

- Every Contract v2 acceptance criterion must link to at least one design element
  and one evidence obligation.
- Every Contract v2 invariant, failure mode, irreversible operation, dependency,
  and blocking or high ambiguity must be addressed explicitly.
- Every component must state one responsibility and its dependencies.
- Every interface reference and data-flow endpoint must resolve.
- Security-sensitive, persistent-state, irreversible, distributed, or
  stochastic intent activates corresponding design and evidence requirements.
- A design's `required_capabilities` may add constraints. It cannot remove
  requirements derived by policy from the Contract or Design IR content.

## Runner capability contract

A trusted runner adapter exposes a versioned capability profile. Initial
capability names cover, at minimum:

- isolated worktree execution;
- ability to pause for external approval;
- controller-state separation;
- artifact fingerprinting and persistence;
- bounded writable paths;
- analyzer invocation or evidence import;
- objective verification;
- secret scanning;
- prohibition of merge and deployment.

The profile distinguishes:

- **declared:** guarantees statically supplied by trusted adapter code;
- **observed:** runtime checks that confirm or reduce those guarantees;
- **effective:** the conservative intersection used by policy.

Task text, model output, generated configuration, and analyzer output cannot
declare capabilities. Runtime observation may reduce an effective capability
but may never elevate one above the trusted declaration. Preflight blocks before
design dispatch or implementation when required capabilities are absent or
unverifiable.

## Analyzer adapter protocol

An analyzer adapter receives an explicitly bounded workspace or evidence file,
the reviewed artifact fingerprint, configured identity, and limits. It returns
a normalized report compatible with `findings_v2` or a typed error. It never
returns `PASS`, `REVISE`, `BLOCK`, approval, or a routing disposition.

The reference release includes:

1. A SARIF importer that normalizes supported SARIF results into findings while
   preserving tool identity, rule identity, severity, locations, and artifact
   binding.
2. A native harness-configuration analyzer that inspects configured project
   instruction, hook, permission, environment, and tool-exposure surfaces
   without modifying them.

Required analyzer failure, timeout, absence, malformed output, stale artifact
binding, or limit violation produces `unavailable` and blocks. Optional analyzer
failure is recorded as degraded and can never satisfy a required evidence rule.
Conflicting findings remain independently visible until an explicit,
artifact-bound resolution is recorded.

## Deterministic design gate

The gate consumes:

- exact Contract v2 bytes, digest, policy result, and current approval;
- exact Design IR bytes and digest;
- design-policy and configuration digests;
- declared, observed, and effective runner capabilities;
- required analyzer reports and their artifact bindings;
- applicable finding overrides or human decisions bound to exact artifacts.

It checks schema integrity, parent identity, traceability, reference integrity,
open questions, risk coverage, capability feasibility, evidence completeness,
analyzer availability, security boundaries, and stale inputs.

Its versioned output records every input digest, deterministic findings, proof
obligations, and one of `pass`, `block`, or `unavailable`. `pass` means policy is
satisfied; it is not human approval. Re-running the gate with identical inputs
must produce byte-equivalent identity-bearing output.

## Approval and readiness

`ArtifactKind.DESIGN` extends the approval store. A design approval records the
exact repository, issue, design digest, and parent Contract digest. Missing,
unreadable, malformed, stale, wrong-parent, wrong-repository, or wrong-issue
records fail closed.

For workflows adopting Design IR, design approval supersedes the opaque T2 plan
approval; it does not add a second approval on top of it. The old plan path
remains available only for compatibility-mode runs.

Any change to identity-bearing Design IR content produces a new digest and
requires new approval. New evidence does not rewrite an existing approval, but
it makes build readiness stale until the gate is rerun against the current
evidence manifest. Evidence that requires a design change therefore leads to a
new digest and approval.

## Operator interface

The release adds:

```text
factory design validate <file>
factory design gate <file>
factory approve design <issue> <digest> --parent <contract-digest>
factory analyze <adapter>
factory capabilities
factory status [issue]
```

Inspection commands support `--json` with versioned output. Human output is
concise and redacted. Existing commands retain their current meanings.

`factory status` reconstructs state from authoritative contract, design,
approval, decision, capability, analyzer, and build records. It reports one of
`ready`, `approval_pending`, `blocked`, `degraded`, `unavailable`, or `complete`,
plus exact artifact digests, gate freshness, effective capabilities, finding
counts, and the next safe action. It performs no repair or mutation and creates
no database.

## Failure and security behavior

The workflow fails closed when a required schema, digest, capability, analyzer,
evidence item, approval, policy version, configuration version, or state record
is missing, unreadable, unknown, stale, malformed, or mismatched.

Additional controls are:

- analyzer paths are contained beneath explicitly allowed roots;
- symlinks and escaping references are rejected;
- analyzer output is size-, count-, encoding-, and schema-bounded;
- malformed findings are quarantined as errors rather than silently dropped;
- secrets and raw tool output are excluded or redacted from status and reusable
  evidence;
- required and optional failures remain distinguishable;
- errors can never be translated into passing evidence;
- 0.3.0 performs no automatic remediation, pack installation, configuration
  takeover, remote write, merge, deployment, or self-promotion.

## Compatibility and migration

Contract v2 and `findings_v2` remain unchanged. Approval and decision readers
remain compatible with existing records.

The configuration adds `factory.build.design_protocol`:

- `design_ir_v1` activates the new T2 path;
- `legacy_plan` retains the 0.2 opaque-plan path;
- a missing value is interpreted as `legacy_plan` with a migration notice so an
  existing project is never silently blocked by upgrade.

Newly generated configurations select `design_ir_v1`. Existing projects migrate
through explicit preview, validation, and opt-in. In-progress runs retain the
workflow protocol recorded when they began. Rollback consists of restoring the
previous configuration for new runs; it does not convert or erase recorded
design state.

Legacy plan approvals remain readable and `factory approve plan` remains
available during v0.x compatibility. A Design IR approval is never inferred
from an old plan approval.

## Release documentation and delivery

The implementation release must update the package version, CLI version,
changelog, README, adoption guide, operating guide, security guidance, known
issues, and a dedicated `docs/releases/0.3.0.md` note wherever the new behavior
changes their claims or examples.

The release checklist must no longer hard-code the 0.2.0 tag or only the 0.2.0
feature set. It must identify the candidate version and expected capabilities
explicitly while preserving separate approvals for branch push, pull-request
creation, merge, tag creation and push, GitHub release, and registry
publication. Release evidence remains outside the public worktree.

No release document may claim that schema validation proves design correctness,
that analyzer coverage is complete, that an approval identity is a
cryptographic signature, or that directory separation is an operating-system
sandbox.

## Verification and release evidence

The implementation must include:

- strict schema, canonicalization, reference, and digest tests;
- pure-rule and combined deterministic gate tests;
- wrong-parent, stale, forged, deleted, and corrupted approval tests;
- capability underclaim, overclaim, and runtime-reduction tests;
- SARIF and harness adapter tests for success, nonzero exit, timeout, absence,
  malformed, oversized, conflicting, partial, and stale reports;
- path traversal, symlink escape, invalid encoding, duplicate ID, injection text,
  credential-shaped data, and unsupported-version tests;
- status determinism, redaction, read-only, and human/JSON consistency tests;
- unchanged 0.2 configuration, plan approval, decision replay, and in-progress
  workflow compatibility tests;
- a synthetic end-to-end path from approved Contract through blocked design,
  corrected design, exact approval, and implementation handoff.

Before release, the clean supported test suite, Ruff, package build, isolated
installation smoke test, documentation examples, public-boundary scanner,
history-range review, and zero-hard-dependency assertion must pass. Migration
and rollback must be exercised against a representative 0.2 project.

Any unresolved critical or high authority, integrity, compatibility, or secret
exposure finding blocks release. Branch push, pull-request creation, merge, tag,
GitHub release, and registry publication require separate approvals.

## Influence and provenance

The operator-experience and lifecycle direction was informed by a review of
[Everything Claude Code](https://github.com/affaan-m/ecc) at commit
`649def769bd860512e5fce86e30aa05c8119259f`. Adopted concepts include explicit
capability visibility, analyzer-style harness inspection, review-oriented
presentation, managed lifecycle planning, and portable context. AIFactory keeps
its own deterministic authority model and implementation. No ECC source or
assets are copied by this design. ECC is MIT-licensed; any later source reuse
would require separate provenance and attribution review.

## Acceptance criteria

Version 0.3.0 is complete when:

1. A strict Design IR v1 document can be validated, canonicalized, stored, and
   replayed against its exact Contract v2 parent.
2. Capability preflight blocks an infeasible design before implementation.
3. Required SARIF or native harness evidence is normalized without acquiring
   disposition authority.
4. The deterministic design gate produces reproducible, input-bound results.
5. Only an exact, current design approval allows the adopted T2 workflow to
   proceed.
6. Status accurately projects readiness and blockers without writing state.
7. Existing 0.2 projects and in-progress runs behave as documented.
8. The adversarial, compatibility, packaging, and public-release gates pass.
