# AIFactory 0.4.0 human review and evidence brief

**Date:** 2026-08-10

**Last revised:** 2026-08-29

**Status:** Roadmap brief; later detailed design approval required

**Depends on:** Stable 0.3.0 Design IR, gate, finding, capability, approval, and
status schemas, plus recorded operational evidence from at least one supported
T2 execution path

## Objective

Make AIFactory's structured contracts, designs, risks, findings, and evidence
understandable and reviewable without moving authority into a user interface or
notification channel.

## User outcomes

- A reviewer can understand what is proposed, why, and which Contract obligations
  it covers without reading raw JSON.
- A reviewer can compare two exact design revisions and see which approval became
  stale.
- Feedback remains anchored to stable artifact and finding identities.
- Acceptance evidence is visibly tied to the exact artifact it supports.
- The operator receives useful approval and blocker notifications without being
  able to approve accidentally from stale context.

## Planned scope

### Review bundle

The core produces a versioned, sanitized `review-bundle-v1` projection containing
artifact identities, traceability indices, findings, decisions, evidence links,
capability gaps, and gate freshness. The bundle is derived from authoritative
records and is never itself authority.

### Review Canvas

A local-first Canvas renders:

- Contract and Design IR summaries;
- component, interface, data-flow, and security-boundary views;
- Contract-to-design-to-evidence traceability;
- risks, unresolved questions, capability gaps, and findings;
- exact revision comparison;
- red/green/unknown acceptance-evidence state;
- the exact approval or revision handoff required next.

The initial implementation should prefer a static or locally served artifact
over a hosted control plane. The detailed design will select the smallest UI
technology that preserves AIFactory's dependency and packaging constraints.

### Anchored feedback

Feedback records bind repository, issue, artifact kind, artifact digest, anchor
ID, author, timestamp, disposition, and rationale. Supported dispositions are
comment, request revision, and reject. Feedback never edits approved bytes in
place. A revision produces a new Design IR artifact and digest.

Approval continues through the core approval path. A Canvas may present or
request that operation only after the core independently re-reads and validates
the exact current artifact. Browser or notification state is not trusted.

### Notifications

Read-only notification adapters may report approval requests, blockers,
unavailable evidence, stale approval, and completion. Messages contain bounded,
redacted summaries and a digest-qualified path back to authoritative review.
They do not accept approval reactions or free-text commands in 0.4.0.

## Authority and security

- A stale Canvas cannot approve or comment on a newer digest.
- All links and anchors are path-contained and identity-checked.
- Raw analyzer output, secrets, private absolute paths, and unrestricted tool
  transcripts are excluded.
- Missing evidence displays as missing or unavailable, never green.
- Review bundles are reproducible projections and cannot override source records.
- Rendering untrusted text must not execute scripts, directives, or remote
  content.

## Non-goals

- Managed configuration changes or repair;
- remote approval bots;
- general project management;
- a new workflow database;
- editing arbitrary repository files;
- organization-wide dashboards or hosted collaboration.

## Entry criteria

- 0.3.0 identity-bearing schemas and status JSON are stable.
- Exact design approval and stale-evidence behavior are proven end to end.
- At least one non-toy supported runner or execution backend supplies and
  observes every capability required for a representative T2 Design IR flow.
- Primary operator platforms have an explicit supported path or safe fallback,
  including a documented disposition for the current macOS APFS
  harness-analyzer limitation.
- Operational evidence records capability gaps, analyzer accuracy and
  availability, design revisions, review time, task outcome, latency, and cost
  within the public/private content boundary.
- The public/private content boundary defines what review bundles may contain.
- A representative set of real review tasks identifies the minimum useful views.

## Adversarial evidence

Tests must cover stale pages, replaced artifacts, malicious Markdown/HTML,
injected links, missing anchors, cross-project IDs, secret-shaped content,
oversized findings, conflicting evidence, unavailable sources, notification
replay, and attempts to manufacture approval through UI state.

Accessibility checks must cover keyboard navigation, focus order, semantic
structure, color-independent status, and readable revision differences.

## Exit and promotion criteria

0.4.0 may ship when:

1. A complete Contract-to-design review and revision cycle works locally.
2. Every displayed claim traces to an authoritative record and exact digest.
3. Feedback round-trips without mutating approved artifacts.
4. Stale, cross-project, and injected review inputs fail safely.
5. Approval still requires the core's independent exact-state validation.
6. Notifications are redacted, replay-safe, and read-only.
7. Accessibility, packaging, compatibility, and public-boundary gates pass.

The 0.5.0 managed lifecycle may depend on the Canvas only after it can render a
configuration change plan and its ownership consequences without acquiring
apply authority.
