# AIFactory 0.3.1 platform paths and factory evaluation brief

**Date:** 2026-10-23

**Status:** Roadmap brief; scope approved for detailed design. Each workstream
below needs its own reviewed design before implementation, except the
diagnostics fixes, which are bounded bug fixes.

**Depends on:** 0.3.0 Contract, Design IR, capability, analyzer, gate, approval,
and status schemas

## Objective

Give the default workflow a supported path on macOS and Linux, give operators
a sandbox they can adopt without building one, and give the project a way to
measure its own outcomes. 0.3.1 produces the evidence the 0.4.0 entry gate asks
for. It adds no new approval authority and changes no released schema.

## Evidence basis

- **macOS blocks the default Design path.** A project containing only
  `CLAUDE.md` and `.claude/settings.json`, on an ordinary APFS volume, produces
  two high-severity harness findings, and new scaffolds require the harness
  analyzer. The findings carry only the text "analyzer finding reported".
- **An APFS clone preserves the source's access time.** On the same volume,
  reading a file updated its access time, while cloning it (`clonefile`) and
  then reading the clone left the source's access time unchanged. This was
  observed on macOS 26 with APFS; the design must re-verify it in tests on each
  supported macOS version rather than rely on this observation.
- **Diagnostics are opaque.** With the scaffold's placeholder repository still
  set, `factory analyze harness` reports only "analyzer inspection is invalid".
  `factory --version` is not supported.
- **The distribution name is taken.** The PyPI names `software-factory` and
  `aifactory` belong to unrelated projects. The README installs
  `software-factory` from Git, so an operator who drops the Git suffix installs
  a different project with a similar purpose.
- **There is no outcome measurement.** The 0.4.0 entry gate requires a
  field-evaluation record, and no tool can produce one.
- **The only non-toy backend requires a custom kernel-level runtime.** Current
  coding-agent products use operating-system sandboxes, default-deny egress,
  and credentials injected outside the sandbox
  ([Anthropic: Claude Code sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing)).
  An Apache-2.0 runtime that applies this pattern to an arbitrary process is
  available ([sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime)).

## Workstreams

### A. macOS no-atime harness reads

When the platform cannot open a file without updating its access time, the
harness analyzer may clone the already-opened, identity-pinned file into
controller-owned scratch space on the same volume and read the clone.

- The clone is taken from the pinned descriptor (`fclonefileat`), so the file
  identity check that already guards the read also guards the clone.
- The scratch directory is controller-owned, outside every worktree, and
  removed after the read. Its creation and removal are not workspace mutations.
- When cloning is unsupported, crosses volumes, or fails for any reason, the
  analyzer keeps today's behavior: a high-severity fail-closed finding.
- Tests prove the source's access time is unchanged on a real APFS volume and
  that every failure path still fails closed.

This preserves the released Design-authority guarantee. Making the required
analyzer optional does not, and is not proposed.

### B. Actionable diagnostics

- `factory --version` prints the installed version.
- Analyzer inspection errors name the failed precondition and the next step,
  for example an unconfigured repository placeholder, without echoing private
  values.
- Harness findings name the file, the reason the read was refused, and the
  required change.

### C. Standard sandbox backend

An optional execution backend that runs the agent process under an
operating-system sandbox and reports observed capabilities through the existing
runner-capability contract:

- bounded writable paths limited to the run's worktree and scratch space;
- default-deny network egress with an explicit allowlist;
- credentials held by the controller and injected outside the sandbox;
- push only to the run's factory branch, and no merge or deployment path; and
- a fail-fast stop on the first denied action, with a bounded reason.

The detailed design chooses the mechanism. The leading candidate is the
sandbox-runtime above on macOS and Linux, with a container fallback on Linux.
The backend remains an optional dependency. The core gains no hard dependency.

### D. `factory eval`

A local evaluation command that measures the factory on a private, held-out
task suite.

- **Task format.** Each task names a repository and base revision, an issue or
  request, and one or more hidden acceptance checks: commands that the
  controller runs in a fresh checkout after the run. Builders and judges never
  receive the checks. A task may also carry seeded-defect variants: a
  known-bad candidate that the judge and quality gates must reject.
- **Arms.** A suite runs the same tasks under several arms, at minimum the full
  factory path and a single-agent baseline on the same runner and model tier,
  so the cost and benefit of each workflow stage are visible.
- **Trials.** Each task runs at least three times per arm.
- **Report.** pass@1 and pass^k (the share of tasks that pass on every trial),
  cost, wall-clock time, human interventions, gate blocks by reason, judge
  verdicts on seeded defects, capability gaps, unavailable analyzers, and
  vacuous checks. Failed and aborted runs are counted, never dropped.
- **Privacy.** Suites, target repositories, transcripts, and raw results stay
  in operator-private storage. The command can emit a redacted summary in the
  `release-readiness-evidence-v1` shape for `factory release readiness`.
- **Authority.** An evaluation result is evidence, never approval. A score
  cannot promote a release, waive a gate, or change routing.

The suite starts small: 15 to 25 tasks drawn from real work in at least two
repositories, at least three of them T2-sized, and at least five
seeded-defect variants.

### E. Publication

Publish under the distribution name `brainmatter-software-factory`, chosen on
2026-10-23 because `software-factory` and `aifactory` belong to unrelated
projects. Publish 0.3.1 to PyPI and update the README install commands. Publication remains a separately approved
shared-state action. The import package name may stay `software_factory`; the
README must state the distribution name explicitly.

## Non-goals

- Changing any released schema, approval rule, or gate decision.
- A public benchmark or leaderboard.
- Shipping task suites or evaluation evidence in the public repository.
- Removing the kernel-level backend, which moves to the containment track.
- Windows analyzer support.

## Exit criteria

0.3.1 may ship when:

1. On macOS and Linux, a scaffold with supported harness files passes the
   harness analyzer without platform-caused high-severity findings, and every
   clone failure path fails closed in tests.
2. Diagnostics name the failed precondition for every analyzer inspection
   error a fresh scaffold can produce.
3. The standard sandbox backend observes every capability a representative T2
   workflow requires, and adversarial tests show write escape, egress outside
   the allowlist, credential reads, and push to a protected branch all denied.
4. `factory eval` runs a suite end to end, reports pass@1 and pass^k per arm,
   counts failed runs, and emits a readiness summary that the preflight
   accepts.
5. A core-only installation still imports and runs its offline suite with no
   backend or evaluation dependency.
6. The README installs `brainmatter-software-factory` and never names a package
   that resolves to a different project.
