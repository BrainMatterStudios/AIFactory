# AIFactory 0.2.0 GitHub Publication Design

**Date:** 2026-08-09
**Target:** GitHub tag and release `0.2.0`
**Repository:** `BrainMatterStudios/AIFactory`

## Goal

Publish the merged architect-first implementation as AIFactory 0.2.0 through a
protected-main, GitHub-only release. The release must make the implemented
capabilities, reasoning, migration path, threat model, and limitations visible
without overstating the experimental builder's assurance.

## Scope

The publication includes:

- a release-preparation pull request that changes release-candidate wording to
  final release wording and records the actual release date;
- agreement among package metadata, CLI version output, changelog, release
  notes, and tag name;
- complete local verification, package-build inspection, public-content scans,
  provenance review, and effective protected-main verification;
- an annotated `0.2.0` tag on the exact merged release commit; and
- a non-draft, non-prerelease GitHub release whose body summarizes and links to
  the comprehensive tracked release notes.

PyPI and every other package registry are out of scope. No deployment or
software-factory repository change is part of this publication.

## Release metadata

`README.md` and `docs/releases/0.2.0.md` will no longer describe 0.2.0 as
unreleased or as a release candidate. `CHANGELOG.md` and the detailed release
notes will use the actual publication date. `pyproject.toml` remains at `0.2.0`.

The GitHub release body will be concise enough to scan while preserving the
reasoning behind the release. It will cover architecture-before-code, exact
digest-bound approvals, the `findings_v2` judge redesign, replayable controller
decisions, public-history scanning, compatibility, and important limitations.
The tracked release note remains the authoritative detailed document.

## Publication flow

1. Prepare and locally commit the metadata and release-body source on
   `codex/release-0.2.0`, based on the current `origin/main`.
2. Run the full documented CI and release checklist against the exact branch
   commit. Stop on any test, lint, build, scan, provenance, or metadata failure.
3. Obtain explicit approval before pushing the release-preparation branch and
   creating its pull request.
4. Let protected-main checks run, review the exact hosted result, and obtain
   explicit approval before merging the pull request.
5. Fetch the merged `main`, repeat release-critical identity and boundary
   checks, and obtain explicit approval before creating and pushing the exact
   annotated `0.2.0` tag.
6. Verify that the remote tag resolves to the reviewed merged commit, then
   obtain separate explicit approval before publishing the GitHub release.
7. Verify the published release URL, tag target, draft/prerelease flags, and
   rendered notes. Do not publish a package.

## Failure handling

No release action is retried by bypassing branch protection, secret scanning,
or required checks. If the candidate changes after verification, all checks
whose evidence depends on its content or identity are rerun. If a remote tag is
unexpectedly present or points at another commit, publication stops for human
resolution; the tag is never moved or replaced automatically.

## Success criteria

- The release-preparation change is merged through protected `main` with all
  required checks passing.
- Package version, CLI version, changelog, detailed notes, and tag all identify
  version `0.2.0` with a consistent publication date.
- Current-tree and reviewed history-range scans report no public-boundary
  findings.
- The remote annotated `0.2.0` tag targets the exact verified release commit.
- GitHub shows a published, non-prerelease 0.2.0 release with the reviewed
  release notes.
- No artifact is uploaded to PyPI or another package registry.
