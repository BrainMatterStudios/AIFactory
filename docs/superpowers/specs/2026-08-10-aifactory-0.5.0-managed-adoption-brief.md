# AIFactory 0.5.0 managed adoption and harness posture brief

**Date:** 2026-08-10

**Status:** Roadmap brief; later detailed design approval required

**Depends on:** 0.3.0 capability/analyzer contracts and 0.4.0 reviewable change
presentation

## Objective

Safely install, inspect, maintain, repair, and remove AIFactory-owned project
harness configuration while preserving user ownership and making drift visible.

## User outcomes

- An operator previews every proposed change before any file is written.
- AIFactory identifies exactly which files or bounded regions it owns.
- Reapplying the same desired state is a no-op.
- User modifications and AIFactory drift are distinguished.
- Repair and uninstall preserve unowned content and have a tested rollback path.
- Runner posture and excessive context or tool exposure are visible before work
  begins.

## Planned scope

### Lifecycle plan and apply

A deterministic planner compares desired managed state, the ownership manifest,
and the current filesystem. It emits a digest-bound change plan with operations,
preconditions, conflicts, backups, and rollback consequences.

Apply revalidates the exact plan digest and every precondition immediately before
mutation. It uses path containment, no-follow operations, same-directory
temporary files, atomic replacement where supported, and a recoverable journal.
Apply authority is separate from design or build approval.

### Ownership manifest

The versioned manifest records:

- project and installation identity;
- managed file or bounded-region identity;
- last-applied content digest;
- ownership mode and merge strategy;
- generator and schema versions;
- backup or restoration metadata;
- capabilities and permissions introduced by the managed content.

AIFactory may replace only content it can prove it owns. Unknown or modified
content becomes a conflict. It is not silently overwritten.

### Drift, repair, and uninstall

Drift is classified as missing, changed-owned, changed-unowned, ambiguous,
unsupported-version, or unsafe-path. Repair is a newly planned and approved
operation, not an automatic side effect of inspection. Uninstall removes only
currently authenticated owned content and restores preserved user content when
the manifest proves how to do so.

### Harness-posture analyzers

Read-only analyzers expand beyond the 0.3 reference collector to inspect:

- project instruction and persona surfaces;
- hooks and lifecycle commands;
- permission and writable-path scope;
- environment and secret-handling declarations;
- runner isolation and controller-state separation;
- enabled MCP or other tool servers;
- context-file size, duplication, and precedence;
- unsupported or conflicting configuration.

Findings use the existing analyzer contract and have no apply authority.

### Context and tool budgets

Configuration may declare explicit maximum context bytes, file counts, tool
servers, and permission classes per runner or workflow. Preflight reports and
blocks policy violations deterministically. A design or pack may request a
stricter budget but cannot weaken the project minimum.

## Authority and safety boundaries

- No global or user-level configuration is modified implicitly.
- Project-level mutation still requires an exact reviewed change plan.
- Inspection, status, and analyzer commands are read-only.
- Repair and uninstall require separate operator authority.
- Unowned edits are preserved unless the operator resolves a displayed conflict.
- No remote marketplace code, self-update, or automatic security remediation is
  introduced.
- A managed configuration cannot elevate the trusted runner capability profile.

## Compatibility and rollback

Unmanaged projects remain valid. Adoption is explicit. The planner can import
existing files only by classifying them as unowned, adoptable after review, or
conflicting; it cannot retroactively claim ownership.

Every mutating operation records enough authenticated local information to
resume, roll back, or stop safely after interruption. Rollback itself revalidates
paths and current ownership rather than restoring blindly.

## Non-goals

- Silent takeover of existing configuration;
- global configuration management;
- unattended repair;
- arbitrary marketplace installation;
- organization fleet management;
- using the Review Canvas as mutation authority.

## Entry criteria

- Capability and analyzer schemas from 0.3.0 are stable.
- The 0.4.0 Canvas can present exact change plans, conflicts, and ownership.
- File-level threat models cover platform-specific path and atomicity behavior.
- Supported runner configuration surfaces are explicitly bounded.

## Adversarial evidence

Tests must cover path traversal, symlink and hard-link substitution, changed
files between plan and apply, partial writes, crashes, stale manifests, corrupt
backups, mixed ownership, overlapping regions, hostile encodings, permission
errors, unsupported versions, repeated apply, repeated uninstall, and attempts
to alter global configuration through project-relative paths.

## Exit and promotion criteria

0.5.0 may ship when:

1. Preview and apply are deterministic and exact-plan-bound.
2. Repeated apply is a no-op.
3. Interrupted operations resume or roll back without losing unowned content.
4. Drift classification is explainable and independently testable.
5. Repair and uninstall affect only authenticated owned content.
6. Harness analyzers and budgets fail closed without mutating configuration.
7. Cross-platform path, compatibility, packaging, and public-boundary gates pass.

The 0.6.0 governed-evolution release may use drift and override history only
after this ownership model can distinguish AIFactory-managed state from user
state reliably.
