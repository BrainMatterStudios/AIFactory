# AIFactory 0.7.0 portable knowledge and ecosystem brief

**Date:** 2026-08-10

**Status:** Roadmap brief; later detailed design approval required

**Depends on:** 0.4.0 review UX, 0.5.0 managed lifecycle, and 0.6.0 governed
admission

## Objective

Move useful, reviewed project context and curated capabilities across supported
runners without transferring hidden authority, leaking context across projects,
or executing unreviewed ecosystem code.

## User outcomes

- A task can resume on another supported runner with explicit provenance and
  freshness.
- Reviewers can distinguish approved artifacts, evidence, decisions, and
  untrusted working memory.
- Capability packs declare what they need before activation.
- Discovery, review, installation, and activation are separate actions.
- An optional dashboard summarizes authoritative state without owning it.

## Planned scope

### Handoff vault

A controller-owned vault stores bounded handoff records containing:

- project and task scope;
- source runner and producer identity;
- source artifact and event digests;
- creation time, freshness, and expiry;
- sensitivity and sharing classification;
- summarized context and unresolved work;
- explicit trust state and review history.

Handoffs are create-only observations until reviewed. They cannot modify source
artifacts, create approvals, satisfy evidence obligations, or move between
projects automatically. Expired or unverifiable context remains visible as
stale but is not supplied to a runner by default.

### Cross-runner transfer

Runner adapters translate only the portable handoff schema and declare any loss
of fidelity. The receiving runner gets the minimum scoped context allowed by
policy. Capability differences are shown before transfer, and an incapable
runner cannot claim that a task can continue safely.

### Curated capability packs

A pack includes immutable content plus metadata for:

- identity, version, provenance, checksum, and license;
- supported AIFactory and runner versions;
- declared capabilities and permissions;
- files, hooks, tools, and context budget introduced;
- configuration schema and defaults;
- tests, evidence, conflicts, upgrade path, and uninstall behavior.

Discovery and inspection never execute pack content. Activation uses the 0.5.0
plan/apply lifecycle, displays all permissions and owned changes, and requires
separate approval. Pack metadata cannot elevate the runner's trusted capability
profile.

### Optional dashboard

A local or separately deployed read-only dashboard may aggregate status,
evidence, handoff freshness, installed-pack posture, and governed-evolution
versions. It consumes versioned projections and owns no workflow state. Loss of
the dashboard cannot stop core CLI inspection or recovery.

## Authority and security

- Memory, summaries, and handoffs are untrusted context, never approval.
- Project, repository, task, sensitivity, and expiry boundaries are enforced
  before retrieval.
- Prompt injection and instructions inside stored context remain inert data.
- Packs are inspected and verified before any lifecycle plan is produced.
- Checksums and signatures prove artifact identity, not safety or quality.
- Pack activation, permission changes, upgrades, and uninstall are distinct
  reviewed actions.
- No default cloud synchronization or organization-wide rollout is introduced.

## Non-goals

- Executing arbitrary marketplace code;
- automatic synchronization of private context;
- treating memory as evidence or authority;
- a hosted service as the only control surface;
- organization fleet management;
- automatic pack activation or permission escalation.

## Entry criteria

- Review projections and anchored identities are stable.
- Managed lifecycle safely installs and removes owned content.
- Governed admission can evaluate curated changes without self-promotion.
- A privacy and retention model covers portable context.
- A pack provenance and license policy is approved.

## Adversarial evidence

Tests must cover tampered provenance, wrong-project retrieval, expired records,
injected instructions, hidden permissions, dependency confusion, capability
overclaim, checksum substitution, malicious archives, path escape, license
conflict, partial activation, failed upgrade, incomplete uninstall, dashboard
staleness, and offline recovery.

## Exit and promotion criteria

0.7.0 may ship when:

1. Cross-runner handoffs preserve provenance and clearly disclose information
   loss and capability gaps.
2. Stale, expired, cross-project, or tampered context is never silently used.
3. Pack discovery and inspection execute no pack content.
4. Activation is exact-plan-bound and uninstall removes only authenticated owned
   content.
5. Packs cannot elevate capabilities or acquire authority through metadata.
6. The optional dashboard is demonstrably read-only and non-essential.
7. Privacy, retention, licensing, compatibility, packaging, and public-boundary
   gates pass.

## Research horizon

Organization policy distribution, hosted coordination, ecosystem registries,
comparative benchmarks, and privacy-preserving aggregate learning remain
unnumbered research candidates. They require new evidence and separate designs;
0.7.0 does not pre-authorize them.
